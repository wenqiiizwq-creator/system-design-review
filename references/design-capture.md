# 设计采集与成稿（模式 A）

工程师负责表达目标、确认取舍；Agent 负责资料分析、专业表达、计算、成稿和复核。
资料包先走 [package-intake.md](package-intake.md)；已有图纸的提取走
[design-reconstruction.md](design-reconstruction.md)。

## 采集与提问

围绕七类意图整理草稿：板卡功能；输入/电源/负载；接口角色与性能；保留/删除约束；
环境与认证；降额/可靠性；成本、供应、生命周期和测试维护。每类有内容或明确未知，
不能把固定问卷的所有问题都当作阻塞项。

先问会改变方向且资料无法回答的内容，一轮少量相关问题，随信息复杂度调整。
资料能确定的由 Agent 查证，不问工程师 datasheet 默认态；目标和权重不明才问其偏好。
问题同时说明已知事实、候选选择和影响。无回答保持 open，继续不依赖该答案的工作。
成本/批量/认证/供应商锁定/实测条件可能改变选型，按相关性补问，不默认为已有要求。

## 来源和冲突

- 目标与允许的取舍由工程师确认；实际实现由适用版本的工程资料支撑。
- 物理约束由精确器件及平台的适用规范支撑，工程师口述不能改变额定值或保证边界。
- 参考设计和旧报告提供线索，冲突先核身份、版本、装配、工况与规范适用性。
- 参数标事实/假设/待确认，记录 kind=intent/implementation/constraint/estimate。
  估算写公式、区间、并发条件和独立核查；与参考现象不符先检查自己的模型。

## 增量文件与工程师确认

维护 `Design_Baseline_<项目>.md` 与 `design-intent.json`，同步版本、需求 ID、决策、
未决项与证据。顶部保留已确认范围、剩余问题、下一步和资料读取状态，便于中断恢复。
早期先交付有用 Markdown 草稿；JSON 增量记录已掌握字段，不为凑齐准出契约拖延成稿，
也不填造占位额定/批准。完整契约用于申请方案准出，缺字段时的门禁错误不阻止继续草稿。
明确书面目标即使 status=open（待当前版本确认），仍是已有目标；用 confirmation_note
说明“原文明确、待候选版本确认”，不要把它当目标未知而要求工程师重复口述。

先完成可审核草稿及资料核验，再向工程师明确展示：确认的版本、需求/决策 ID、
拟采用的选择和未决项。真实回复记录 actor/source_id/locator/scope；不得伪造接受。
确认“这是需求”和证明“满足需求”是独立动作；先前有效授权/确认可继续使用。

确认记录的 scope 可为 `requirement:<id>`、`decision:<id>` 或明确确认整份 `baseline`。
非关键风险接受与移交接收分别需显式 `risk:<plan_id>`、`issue:<id>`、`handoff:<id>`，
不能以通用“方案看过了”自动补出。数据契约规定的内容摘要用于检测过期，不是签名。

优化改了目标/轨/接口/能力时，重验并确认受影响内容；纯位号映射不重问原意图。
保留旧版和决策来源；不同基线版本的旧确认留在历史产物，不能复用到新版本门禁。
A 草稿完成后必须跑 B；在待确认阶段可先审查独立模块，并写明结论条件。
