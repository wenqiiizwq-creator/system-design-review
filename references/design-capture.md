# 设计采集与成稿协议（模式 A）

目标：工程师只说自然语言，AI 负责分层采访、翻译成专业设计语言、增量成稿。
工程师的负担只在“回答问题 + 审签结果”，不要求他先写设计文档。

## 输入来源与优先级

1. 对话中工程师的原话（最高权威；但口述可能前后矛盾，冲突必须当面澄清）
2. 板卡相关文件：历史设计文档、框图、BOM、旧原理图 PDF、平台设计指南、同类项目
3. 核心器件 datasheet：Absolute Maximum Ratings、引脚语义、推荐应用电路、
   强制条款（must / shall / must not）
4. Hardware-Wiki（平台规则与既有设计），可用时检索

同源冲突：对话 vs 文件冲突 → 标出冲突点并请工程师裁决，不悄悄选一边。

## 分层采访（每轮批量 3–5 问）

**第一层：7 个意图块**（先全部过一遍，再下钻）：

1. 板卡功能一句话
2. 电源链路：输入来源/范围 → 各中间轨 → 各负载与功耗预算
3. 接口清单与各自角色（Host/Device、协议、电压）
4. 必须保留 / 必须删除的内容
5. 环境约束：温度、振动、防护、EMC/认证
6. 降额与可靠性策略
7. 特殊约束：成本目标、供应商锁定、绑定芯片、平台强制规则、可测试性

**第二层：按模块下钻**，顺序：电源 → 外设/接口 → 功能链路 → 关键选型。

提问纪律：

- 每轮 3–5 个问题，按“能改变架构方向”优先于“参数细节”排序。
- 资料能定的不问人：datasheet 推荐电路、引脚默认态、平台强制规则。
- 必须主动问的隐性约束：成本目标、认证、供应商/替代料限制、EMC 历史、
  测试/可维护性、批量与生命周期。
- 拒绝沉默默认：工程师未答且资料无出处 → `[XXX]` 待确认，绝不编。
- 每个关键决策记录来源：对话轮次 或 文件:页码。

## 增量成稿

每轮对话结束立即更新项目目录下两份文件：

- `Design_Baseline_<项目>.md`：人读基线（结构见 `references/report-template.md`）
- `design-intent.json`：机器可校验的结构化基线（契约见
  `references/design-intent-schema.md`）

参数三分类，逐项标注：

- **事实**：有出处（文件:页码、datasheet:表号、对话轮次）
- **假设**：AI 推断，必须写推导依据（公式、参考设计、同类平台）
- **待确认**：`[XXX]` 占位，进“待确认清单”

断点续：基线文档顶部维护“状态摘要”——已确认模块、待确认清单、下一轮问题队列。
对话中断后凭它继续，不重复采访已确认的内容。

## 反幻觉硬规则

- datasheet 引用 = 文档名 + 版本 + 页码/表号；聚合页不采信，网络补取要留
  URL + 获取日期，补取文件放 /tmp，不混入项目资料。
- 电流/功耗/温度等数字：写来源或标假设；估算必须写公式与假设区间。
- 算出的轨压/功耗至少与一个独立迹象对撞；对不上先怀疑自己的计算。

## 完成门禁（进入模式 B 前）

- 7 个意图块每块都有内容，或显式 `[XXX]` 待确认；
- 核心器件 datasheet 已核对（身份、Abs Max、关键强制条款）；
- 隐性约束逐项声明（已确认 / 待确认），不存在“没问就默认掉”的项。
